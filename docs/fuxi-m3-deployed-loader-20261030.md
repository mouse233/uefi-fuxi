## 旧 lookup 格式为何会返回2

旧IQSEEComCompatAppLoader.h固定SHA为597124e1…22a06，其lookupTA为BI1/OO1。
M3SmciDiagnostic.inc当前旧代码也明确写Lookup=TRUE;Op=2;Counts=0x1001。
这是已验证的参考契约，但它**不是当前部署固件的完整lookup契约**。

当前invoke以ObjectArg的16字节本地结构处理：

```text
arg[0] BI：名字指针 / 名字长度
arg[1] BO：架构输出指针 / 容量4
arg[2] OO：返回对象对
counts = BI1 + BO1 + OO1 = 0x1011
```

keymaster64与keymaster两种公开名字，分别运行旧0x1001、新0x1011但BO容量3/8、
以及新0x1011/BO4，共8组控制。前三种均真实返回2，没有名字读取或分配；正确
格式越过该门，再在未覆盖的注册表入口15732c18停止。**通过格式门不等于真实
lookup成功或有权限。** 没有把后续注册表查询返回值替代成成功。

这为旧实机lookup=2提供当前代码中可复现的格式解释，但旧上机并未绑定当时
运行TZ及返回PC，不能倒填为那一轮的实际分支。它也不是密钥恢复-62的已证根因。

后续查询候选应仅更改这项契约，保持root/open122/查已有对象/验证架构/释放的
边界。沿用已验证SMCI描述符规则推导出的待实机线格式为：

| 字段 | offset / 内容 |
| --- | --- |
| 头 | 句柄、op2、counts1011 |
| BI描述符 | +12：名字offset40、length11 |
| BO描述符 | +20：架构offset56、capacity4 |
| OO描述符 | +28：初值0/0，返回句柄位置不同于旧+20 |
| 名字 | +40：keymaster64，不含结尾NUL |
| 架构 | +56：4字节，只接受ELF class1/2 |

该表是当前内部契约与既有封送规则的推导，**不是已实测的完整NS消息**；本轮
模拟从已解码的ObjectArg入口进入，没有运行SMCI反序列化。不能只改counts后仍
把+20当返回句柄，或绕过架构、未识别对象及回调/清理检查。

## loadFromBuffer 确有缓存复用分支

op1先复制/检查名字，再调用157335a8。该函数在157acf50/157acf60两个列表上
经157336c8查找：名字匹配时增加节点引用；随后15733490仅分配32字节兼容包装
对象，包装中仍指向同一缓存节点。第二列表成功时还会移到第一列表。

主机提供私有公开合成节点、名字和架构位，普通分配/清零/复制/释放作精确有界
模型，没有伪造注册、认证、RPC或TA初始化。4组缓存控制的结果：

- 第一列表直接命中：真实代码返回兼容对象，节点引用1→2，架构字节0/1分别
  输出ELF class1/2。
- 第二列表分支：第一列表即使空，也可能先访问未覆盖的注册表。为独立观察
  第二列表，从真实返回点**明确注入第一列表非成功结果11**，其余匹配/包装/
  移表/架构输出指令真实运行。它不是实际第一列表miss或设备缓存证明。

完整op1的4组路由（第一/第二/空/不同名私有缓存）中，仅第一列表命中路径在
distName输出15733820前停，其余在注册表前停。所有路径均未读取传入的合成
无效ELF，不能推断它被接受；复用路径本来就能先于新ELF处理到达对象包装。
这给“loadFromBuffer可能复用”补上了实际代码依据，**不证明本轮设备已复用**。

另两个非成功返回点控制在157335a8调用前保留op1真实帧，再从1569db68注入
内部结果11/5：11进入新加载所需的环境查询15686d04前停止，5进入状态映射
157350f0前停止。内部结果11不等同于公开头文件中同数值错误；没有运行新加载、
解释实际错误值或替代这些辅助函数成功。
